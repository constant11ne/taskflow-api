# TaskFlow API

Я сделал небольшой сервис для задач на FastAPI. В нём я создаю задачи, выбираю приоритет, меняю статус, ищу нужное и смотрю, сколько уже сделано. Чтобы каждый раз не отправлять запросы вручную, я добавил простую страницу по адресу `/`. Когда мне нужно проверить само API, открываю `/docs` со Swagger UI.

Я не стал подключать базу данных и авторизацию: для учебного проекта это лишняя настройка. Задачи хранятся в памяти одного процесса и исчезают после перезапуска сервера. Поэтому запускаю приложение без `--workers`.

## Что я добавил

- Создание, просмотр и удаление задач, смену статуса между `todo`, `in_progress` и `done`.
- Приоритеты `low`, `normal`, `high`, поиск по названию, фильтры и пагинацию.
- Статистику по статусам и процент выполненных задач.
- Проверку входных данных, понятные HTTP-ошибки, настройки через окружение и логи.
- Веб-страницу, автоматические тесты и workflow для GitHub Actions.

Основной код у меня в `app_final.py`, интерфейс — в `web/index.html`, тесты — в `test_app.py`. Зависимости записаны в `requirements.txt` и `requirements-dev.txt`. Конфигурация запуска PyCharm лежит в `.run/TaskFlow_API.run.xml`.

## Как я запускаю проект

Мне нужен Python 3.12. В терминале я перехожу в папку проекта и создаю виртуальное окружение.

macOS / Linux:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
```

Windows PowerShell:

```powershell
py -3.12 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
```

Если мне нужно только запустить сервис без тестов, я устанавливаю `requirements.txt`. Файл `.env` необязателен: стандартные настройки уже работают. Когда хочу их поменять, копирую `.env.example` в `.env` и редактирую копию. Настоящий `.env` и `.venv` в Git не попадают.

Запускаю сервер из корня проекта:

```bash
python -m uvicorn app_final:app --host 127.0.0.1 --port 8000
```

После этого открываю [страницу с задачами](http://127.0.0.1:8000/). Там я могу добавить задачу, сменить статус, воспользоваться поиском и увидеть обновлённую статистику. Для проверки отдельных запросов открываю [документацию API](http://127.0.0.1:8000/docs): выбираю маршрут, нажимаю **Try it out**, заполняю параметры и отправляю запрос через **Execute**. Сервер останавливаю сочетанием `Ctrl+C`.

В PyCharm я открываю папку проекта, выбираю интерпретатор `.venv/bin/python` (на Windows — `.venv\Scripts\python.exe`) и запускаю готовую конфигурацию **TaskFlow API**. Если PyCharm её не подхватил, создаю Python-конфигурацию вручную: **Module name** — `uvicorn`, параметры — `app_final:app --host 127.0.0.1 --port 8000`, рабочая папка — корень проекта.

## Как устроено API

| Метод | Маршрут | Что я получаю |
| --- | --- | --- |
| GET | `/` | Страницу для работы с задачами |
| GET | `/health` | Проверку, что сервис отвечает |
| GET | `/version` | Название и версию приложения |
| GET | `/tasks` | Список задач с поиском, фильтрами и пагинацией |
| POST | `/tasks` | Новую задачу |
| GET | `/tasks/{task_id}` | Одну задачу по ID |
| PATCH | `/tasks/{task_id}` | Задачу с новым статусом |
| DELETE | `/tasks/{task_id}` | Удаление задачи |
| GET | `/stats` | Статистику по задачам |

Например, так я создаю задачу и отмечаю её выполненной:

```bash
curl -X POST http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"Подготовить итоговый проект","priority":"high"}'

curl -X PATCH http://127.0.0.1:8000/tasks/1 \
  -H 'Content-Type: application/json' \
  -d '{"status":"done"}'

curl http://127.0.0.1:8000/stats
```

Здесь `1` — ID первой задачи после запуска; в реальной работе я беру ID из ответа на создание. Поиск задаю параметром `q`, статус и приоритет — параметрами `status` и `priority`. Для страниц использую `limit` от 1 до 100 и `offset` от 0. Название задачи должно быть длиной 1–120 символов, описание — не больше 1000; пустые названия и лишние поля API отклоняет.

## Настройки

| Переменная | По умолчанию | Для чего я её использую |
| --- | --- | --- |
| `APP_NAME` | `TaskFlow API` | Название сервиса |
| `APP_VERSION` | `1.0.0` | Версия в `/version` и OpenAPI |
| `MAX_TASKS` | `1000` | Максимальное число задач в памяти |
| `LOG_LEVEL` | `INFO` | Подробность логов |

После изменения `.env` я перезапускаю сервер. Некорректный лимит или уровень логов обнаруживается при запуске, а уже заданные системные переменные имеют приоритет над `.env`.

## Как я проверяю работу

Локально я запускаю:

```bash
python -m pip check
python -m pytest -v
```

Тесты проверяют создание и изменение задач, поиск, фильтры, пагинацию, статистику, настройки, логи и ответы при ошибках. Они используют отдельные экземпляры приложения, поэтому не трогают задачи в работающем сервере.

Я также добавил `.github/workflows/ci.yml`. Если проект находится на GitHub, после `push` или `pull_request` GitHub Actions установит зависимости, выполнит эти проверки и при успехе приложит ZIP-архив к запуску. Сам файл workflow ещё не означает, что конкретный запуск прошёл успешно: результат я смотрю во вкладке **Actions**.

Если что-то не работает, сначала проверяю `http://127.0.0.1:8000/health`, выбранный интерпретатор и вывод сервера в терминале PyCharm. Ошибка `Address already in use` обычно значит, что порт 8000 занят; тогда останавливаю прежний процесс или меняю порт. После перезапуска список задач пустой — это ожидаемо для хранения в памяти.

## Почему я сделал именно так

Мне хотелось показать не только набор эндпоинтов, но и работающий небольшой продукт, который можно открыть в браузере. Поэтому я добавил интерфейс и тесты, а инфраструктуру оставил простой. Для этого задания мне важнее понятная логика задач, проверка ошибок и воспроизводимый запуск, чем база данных или развёртывание отдельного сервера.
